# Runtime canvas audit — September 9, 2026

The game had several gaps in canvas ownership. Those gaps are corrected: the player-facing screens receive live window geometry through `RuntimeCanvas`, their outer bounds cannot be resized by their children, and the loose menu/HUD controls now have canvas-derived placement. The separate editor, generated simulation reports, and operating-system control internals retain their own layout systems.

The inventory covers 168 Swift, Metal, header, and plist files across Engine, Liberty Line, LevelEditor, and Simulator. It identifies 46 files with view/render declarations or drawing entry points, plus the Simulator's generated HTML report. Database-backed virtual-canvas and HUD definitions were also traced through their DAOs. Saved QA programs and historical reports under Tools are development artifacts, not game screens.

“Canvas-derived” means a dimension or position comes from the live physical rectangle, safe rectangle, playable rectangle, projection scale, or a child frame resolved from those values. Authored coordinates, image aspect ratios, proportional animation effects, readable-size limits, and minimum touch targets remain valid inputs. This does not require every leaf view to accept a RuntimeCanvas argument or every dimension to scale without limits.

| Rendering surface | Geometry authority and audit result |
| --- | --- |
| App/window root | `WindowReader` observes the hosting window's bounds and safe area. `ScreenGeometryGate` refreshes RuntimeCanvas when either changes. `ScreenCanvas` supplies the absolute origin; `RuntimeCanvasView` fixes the screen proposal. |
| Gameplay map layers | `LevelMapArt` and `LevelMapProjection` fit the authored VirtualCanvas to `runtimeCanvas.playAreaRect`. Terrain, paths, overlays, and occlusion use that projection. |
| Towers, heroes, enemies, militia, projectiles | World positions use the map projection. `MapSpriteScale(runtimeCanvas:)` now takes its scale and playable height directly from the same live canvas. Existing sprite/readability clamps remain. Ground offsets, health bars, selection rings, and projectile rotations are relative to those resolved frames. |
| Tower slots and tap areas | Slot art uses projected map dimensions. Tap areas use `SlotTapTarget`, including its touch floor. Debug slot numbers now scale from the projected slot. |
| Build/upgrade/confirm/cost/rally controls | `TowerMenuLayout` resolves authored menu dimensions using the runtime scale. Icons, badges, rally buttons, and their positions derive from that resolved menu. |
| Range rings, destination gestures, rally flash, defeat presentation | Runtime range conversion and map projection determine geometry. `LevelViewport` independently fixes map, HUD, and presentation layers to the physical canvas. Presentation ordering remains handled by `PresentationStack`. |
| Stats, speed/pause, misc controls | Section dimensions come from RuntimeCanvas/HudSizing. Each configured edge/corner is now independently anchored to `hudRect`, preventing neighboring content from shifting its position. |
| Hero/reinforcement bar | `HeroBarLayout` resolves the row inside the authored lower-left occlusion and live HUD rectangle. Portraits, cooldowns, and selection decoration use its button dimensions. |
| Call-wave controls | Authored map centers transform through `CallWaveButtonLayout(runtimeCanvas:)`; button, portrait, countdown, and pulse use the resolved frame. |
| Campaign background | The Metal view receives an explicit physical-canvas size. Crop geometry now uses that logical size and the same authored image coordinates as the SwiftUI markers. Drawable pixels remain a rasterization detail. |
| Campaign markers/tethers/decor/compass/title/menu | The physical canvas feeds crop projection, collision placement, and decorative frames. Title/MenuBar layouts use RuntimeCanvas and HudSizing. |
| Heroes grid/details | Grid art derives from a playable content rectangle that reserves the Done footer. Detail art/text use canvas-scaled metrics. Done is explicitly sized and positioned. |
| Encyclopedia and shop/upgrades placeholders | Authored composition frames or scaled metrics derive from RuntimeCanvas. Done is explicitly sized and positioned. |
| Level briefing | Shared projected map preview and canvas-scaled cards. The content rectangle reserves the footer; the card scale also accounts for available height. Descriptions have room for four lines. |
| Settings/HUD layout configuration | Settings content uses the safe rectangle and scales its insets. The configuration board is explicitly centered in the playable rectangle. Done has a defined canvas frame. |
| Debug guides/readouts/haptic audition | Guides draw RuntimeCanvas rectangles/paths. Readout and audition text/padding now use canvas metrics; the stats readout is an overlay and cannot resize the counter strip. Fine strokes and native controls retain optical/platform sizing policies. |

The concrete corrections include the startup-only window measurement, selection of an arbitrary connected scene, unbounded menu Done buttons, implicit HUD section placement, the top-left configuration board origin, duplicate sprite-fit inputs, and the Metal crop's independent geometry input. `WindowReader.swift` is now included in the Xcode app target. A nearly transparent asset-preload group is hidden instead of drawing a faint pixel.

Visual verification caught two additional problems: Done covered the final hero label, and the minimum briefing overlapped its footer. Both now reserve footer space before content layout. Difficulty descriptions no longer truncate in the reviewed fixtures. Existing game artwork files and world-size settings were not edited.

**Validation:** the unsigned Debug iOS device build passed, including the project's Washington asset verification. All 81 Swift tests passed. New coverage exercises safe-area fits, asymmetric insets, shared sprite/range scale, footer exclusion, and fixed screen sizing with zero, unspecified, small, and oversized child proposals. The existing viewport regressions remain passing.

The isolated UIKit probe passed four phases: normal window, oversized UI, a resize from 874×402 to 740×360 with changed safe insets, and restoration. Screen/map frames followed the actual window; a projected marker followed the playable center; the stateful screen kept the same identity. Seven production SwiftUI screens were captured at both the simulator's 874×402 window and a synthetic 604.44×340 reference canvas, at 1× and 3×. The small captures were inspected before enlargement. The existing readability lab also resolved the Done artwork at its actual 35.65-point minimum.

The complete game cannot compile for this simulator SDK because the project's existing Metal 4 interfaces are unavailable there. The UI capture app therefore compiles the production SwiftUI screens and Engine code, excludes the Metal campaign renderer, and loads the built assets into its own sandbox. These are production-view captures, not full-game navigation or Metal runtime tests. Physical-device play, every hero detail, all HUD configurations, all gameplay states, Dynamic Type/localization, and extreme multitasking sizes remain unmeasured.

**Remaining boundaries:** LevelEditor toolbars, inspector, split panes, and playtest charts use native SwiftUI layout with fixed point metrics. Editor map/playtest canvases use VirtualCanvas plus `DesignTransform` and editor zoom; selected HUD/wave previews also construct local RuntimeCanvas values. `Simulator/FocusReport.swift` generates browser CSS/SVG layouts. The unused `TiledBackgroundMetalView` still uses texture/drawable ratios and has no active game call sites. Native switches, menus, system popovers, and thin decorative strokes are not all uniformly scaled by RuntimeCanvas. Those are explicitly recorded exceptions to a literal “every rendered thing in the entire repository” requirement.

Evidence is in [the audit record](reports/runtime-canvas-2026-09-09/README.md), including [the source inventory](reports/runtime-canvas-2026-09-09/source-inventory.json), [UIKit results](reports/runtime-canvas-2026-09-09/uikit-results.json), test/build logs, and before/after screen captures. Reproduce the automated checks with `swift test`, `Tools/check_runtime_canvas.py`, and `Tools/capture_canvas_screens.py`; each probe's `--help` lists its required simulator/resource arguments.
